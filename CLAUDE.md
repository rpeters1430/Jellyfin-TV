# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"Jellyfin TV" (`com.example.jellyfintv`) is a native Android TV client for Jellyfin media servers, built with Jetpack Compose + androidx TV Compose (`tv-foundation`/`tv-material`) and Media3 ExoPlayer. Single Gradle module: `app`.

## Common commands

Run from the repo root (Windows: use `gradlew.bat`, or `./gradlew` from Git Bash).

- Build debug APK: `gradlew.bat assembleDebug`
- Install on connected device/emulator: `gradlew.bat installDebug`
- Run unit tests (JVM, `app/src/test`): `gradlew.bat test`
- Run a single unit test class: `gradlew.bat test --tests "com.example.jellyfintv.data.repository.JellyfinRepositoryTest"`
- Run instrumented tests (`app/src/androidTest`, requires device/emulator): `gradlew.bat connectedAndroidTest` — currently empty, see Testing below
- Lint: `gradlew.bat lint`

## Testing

Unit-tested (JVM, `app/src/test`): `JellyfinRepository`, `HomeViewModel`, `MediaDetailViewModel`, `LibraryViewModel`, `SearchViewModel`. No Compose UI/instrumented/screenshot tests exist (`app/src/androidTest` is empty). This was a deliberate scoping choice (business-logic coverage first, established early rather than retrofitted later), not an oversight; ask before assuming UI-level testing is out of scope long-term.

`SearchViewModel`'s debounced search (`delay(300)` before calling `repository.searchMedia()`) needs virtual time control beyond what the other ViewModel tests require: `MainDispatcherRule.testDispatcher` is exposed (not `private`) specifically so `SearchViewModelTest` can call `testDispatcher.scheduler.advanceUntilIdle()` after `onQueryChange()` to let the debounce elapse — that scheduler is what `Dispatchers.Main` actually runs on inside the test and is independent of `runTest`'s own scheduler, so `runTest`'s automatic advancement doesn't reach it.

- `JellyfinRepositoryTest` runs the repository against a real local **MockWebServer** (`okhttp3.mockwebserver`) rather than mocking `JellyfinApi`/Retrofit — `RetrofitClient.getApi()` already takes an arbitrary base URL, so pointing `prefs.serverUrl` at the MockWebServer instance exercises the real Retrofit/OkHttp/Gson wiring with no source changes needed. Uses `FakeServerPreferences` (see below) instead of a real `Context`.
- `HomeViewModelTest`/`MediaDetailViewModelTest` mock `JellyfinRepository` directly with **MockK** (`mockk<JellyfinRepository>(relaxed = true)` + `coEvery`) rather than extracting a repository interface — MockK can mock concrete/final Kotlin classes on the JVM without any production-code changes, so this was preferred over a repository-interface extraction to keep the DI footprint minimal. State assertions use **Turbine** (`viewModel.uiState.test { awaitItem() }`). Both test classes apply `@get:Rule val mainDispatcherRule = MainDispatcherRule()` (`app/src/test/java/com/example/jellyfintv/MainDispatcherRule.kt`) to swap `Dispatchers.Main` for `UnconfinedTestDispatcher` — required for `viewModelScope.launch` to run at all in a JVM test, and its eager/synchronous execution means the ViewModel's `init { load() }` has already finished by the time the test starts collecting, so tests read the settled state directly rather than stepping through loading states.
- `ServerPreferences` is an interface for exactly this reason: `AndroidServerPreferences` (real, `SharedPreferences`-backed, needs a `Context`) is the only implementation in `main`; `FakeServerPreferences` (in-memory, in `app/src/test`) is a straight fake for tests. This was a deliberately small, single-class extraction — not a general DI push — see `JellyfinRepositoryTest`/`FakeServerPreferences` for the pattern to reuse if another class needs the same treatment.
- Regression tests worth knowing about if you touch that code again: `JellyfinRepositoryTest` asserts `reportPlayingProgress`/`reportPlayingStopped` actually put `ItemId` in the request body (this was silently broken before — see `PlaystateRequest` note below), and that `getStreamUrl()`/`getStreamHeaders()` never leak the token into the URL.

## Architecture

### Navigation

`MainActivity.kt` is the entire navigation layer: a hand-rolled `sealed class Screen` (`Connect`, `Home`, `Search`, `Library`, `Detail`, `Player`) held in a single `mutableStateOf<Screen>`, switched on directly inside `setContent`, with manual per-screen `BackHandler` logic. All real screens (`ConnectScreen`, `HomeScreen`, `SearchScreen`, `LibraryScreen`, `MediaDetailScreen`, `PlayerScreen` in `ui/screens/`) are wired up here and take `repository: JellyfinRepository` directly — there's no separate nav library, router, or DI layer. Follow this pattern for new screens rather than introducing one.

(An unused Navigation3 + template `DataRepository`/`MainScreenViewModel` scaffold shipped with the original Android Studio template and has been removed — if you see references to it in old branches/PRs, it was dead code, not a second navigation system to reconcile with.)

### Data flow

- `JellyfinRepository` (`data/repository/JellyfinRepository.kt`) is the single facade the UI talks to, constructed once in `MainActivity` and passed down to every screen. Every method returns `Result<T>`; failures are `Result.failure(UnauthorizedException(...))` on HTTP 401 (screens should treat this as "log the user out") versus a plain `Exception` for other failures (screens should show a retry state) — see `HomeScreen`/`MediaDetailScreen` for the pattern.
- `RetrofitClient` (`data/api/RetrofitClient.kt`) builds/caches a Retrofit+OkHttp client keyed by `(baseUrl, trustSelfSignedCerts)`. By default it validates TLS certs against the system trust store like any browser; it only bypasses validation entirely when `ServerPreferences.trustSelfSignedCerts` is `true`, which the user opts into per-server via a checkbox in `ConnectScreen`. `RetrofitClient.buildOkHttpClient()` is also reused directly by `PlayerScreen` (via `OkHttpDataSource`) so video streaming honors the same cert-trust setting as the API client. Logging is capped at `Level.BASIC` (method + URL + response code) — never raise it to `HEADERS`/`BODY`, since request bodies/headers carry the plaintext password (login) and bearer token (every other call).
- Auth uses Jellyfin's `MediaBrowser` auth-header scheme (built in `JellyfinRepository.getAuthHeader()`, sent as the standard `Authorization` header — not OAuth/Bearer tokens, and not `X-Emby-Authorization`). Jellyfin's `AuthenticateNewSessionInternal` requires `Client`/`Device`/`DeviceId`/`Version` to all be present in that header or every request 400s; only send it as `X-Emby-Authorization` if you also need to support servers with the (off-by-default) `EnableLegacyAuthorization` setting. Video stream requests carry the same header via `JellyfinRepository.getStreamHeaders()` rather than an `api_key` query param, so the token never ends up baked into a URL (and therefore into logs).
- `PlaystateRequest` (`data/model/JellyfinModels.kt`) must always be constructed with named arguments — it previously had no `ItemId` field and a positional call was silently stuffing the item ID into `MediaSourceId`, so resume-position reporting was a no-op against the real Jellyfin API. `JellyfinRepository.reportPlayingProgress`/`reportPlayingStopped` are the only call sites; keep them using named args.
- `ServerPreferences` (`data/preferences/ServerPreferences.kt`) is an interface; `AndroidServerPreferences` persists server URL/token/userId/username/`trustSelfSignedCerts` in `SharedPreferences` and is the source of truth for `isLoggedIn`. `MainActivity` constructs `AndroidServerPreferences` directly (see Testing below for why it's an interface).
- **Demo mode**: entering `"demo"` as the server address in `ConnectScreen` sets `prefs.serverUrl = "DEMO"`. `JellyfinRepository.isDemoMode` then short-circuits every method to return canned data from `SampleMediaData` (movie posters/backdrops point at Unsplash URLs, playback streams a public Big Buck Bunny sample). When touching repository methods, preserve the demo-mode branch.
- `authenticate()` tries multiple candidate URLs in order (as-typed, then `https://`/`http://` with default Jellyfin ports 8096/8920) to make onboarding forgiving about what the user types.

### UI structure

- `ui/screens/` — top-level screens (`ConnectScreen`, `HomeScreen`, `SearchScreen`, `LibraryScreen`, `MediaDetailScreen`, `PlayerScreen`), each taking `repository: JellyfinRepository` directly (no DI container). `HomeScreen`/`HomeViewModel`, `MediaDetailScreen`/`MediaDetailViewModel`, `SearchScreen`/`SearchViewModel`, and `LibraryScreen`/`LibraryViewModel` extract their async loading/error/retry logic into a plain `ViewModel` exposing a single `StateFlow<UiState>` (loading/error(retry)/content tri-state, 401 → `sessionExpired` → screen calls `onLogout()`); follow this pattern for new data-fetching screens rather than holding fetch state directly in the composable. `SearchViewModel` debounces query changes (300ms) before calling `repository.searchMedia()`, cancelling the prior in-flight search job on each keystroke. `LibraryViewModel` takes `parentId`/`collectionType`/`mediaType` constructor params to decide which repository call to make and re-fetches on `setSort()` (see `LibrarySort`). `ConnectScreen` (simple form state) and `PlayerScreen` (state is really ExoPlayer's, tightly bound to `Context`/lifecycle) intentionally still hold their own `remember` state rather than using a ViewModel.
  - ViewModels are created via `viewModel { ... }` / `viewModel(key = ...) { ... }` (no `ViewModelProvider.Factory` boilerplate — `androidx.lifecycle.viewmodel.compose.viewModel`'s lambda-initializer overload). **`MediaDetailViewModel` must be created with `key = itemId`** (and `LibraryViewModel` similarly needs a key derived from its params): there's no Navigation library here, so every screen shares the same Activity-scoped `ViewModelStore`, and without an explicit key, navigating to a second, different item/library would silently reuse the previous cached `ViewModel`/data instead of loading the new one.
- `ui/components/` — reusable TV-focused composables (`HeroBanner`, `MediaCard`, `MediaRow`, `AppNavHeader` — the persistent top nav bar with library icon lookup via `getLibraryIcon()` — and `TvTextField`, the one D-pad-focus-styled text input every screen with a text field uses; `AuthenticatedAsyncImage` wraps Coil's `AsyncImage` to attach the `Authorization` header to poster/backdrop requests instead of an `api_key` query param, so the token never ends up in a URL that OkHttp's request-line logging could pick up). Only use `androidx.compose.material3` imports for the handful of things `tv.material3` doesn't provide (e.g. `CircularProgressIndicator`) — always alongside `import androidx.tv.material3.*`, never a bare `import androidx.compose.material3.*`, since that silently shadows `Text`/`Icon`/`MaterialTheme.typography` with M3's versions, which `JellyfinTVTheme` (built on `tv.material3.MaterialTheme`) never populates.
- `ui/theme/Theme.kt` defines the real app theme (`JellyfinTVTheme`, a fixed dark TV color scheme) — there is no other theme file to confuse it with.
- `PlayerScreen` uses Media3 ExoPlayer with a custom `OkHttpDataSource` (auth headers, shared TLS trust config) and HLS support. Every back-navigation path goes through `exitPlayer()`, which reports the final position via `reportPlayingStopped` before calling `onBack()`; `onDispose` also fires a best-effort report as a fallback for exit paths that bypass `exitPlayer()` (e.g. `MainActivity`'s system-level `BackHandler`). Playback errors surface via `Player.Listener.onPlayerError` with a retry/back overlay rather than failing silently to a frozen black screen.

### Auto-update

The app is sideloaded (not distributed via Play Store), so it self-updates by checking GitHub Releases rather than relying on a store. `UpdateViewModel` (`ui/screens/UpdateViewModel.kt`) is constructed once in `MainActivity` — deliberately Activity-scoped, not per-screen, since the update prompt (`ui/components/UpdateDialog.kt`) needs to be able to surface as an overlay regardless of which `Screen` is currently showing (it's rendered as a `Box` overlay alongside the `when (currentScreen)` content, not inside any individual screen). It checks once per process launch (`init { checkForUpdate() }`), fails silently on error (a failed background check shouldn't interrupt the user — it just tries again next launch), and never nags: `dismiss()` only clears the current prompt for this process lifetime, it doesn't persist a "skip this version" preference.

`AppUpdateManager` (`data/update/AppUpdateManager.kt`) does the actual work: hits `GET repos/{owner}/{repo}/releases/latest` via a small dedicated `GithubClient`/`GithubApi` (deliberately separate from `RetrofitClient` — that one's cache key is tied to the user's configured Jellyfin server URL/TLS setting, an unrelated concern), compares the release's `tag_name` against the installed `versionName` (read via `PackageManager`, not `BuildConfig` — `buildFeatures.buildConfig = false` in `app/build.gradle.kts`) using `AppUpdateManager.isNewerVersion()` (a pure, unit-tested numeric-segment comparison — plain string comparison would incorrectly rank "1.9.0" above "1.10.0"), downloads the first `.apk` release asset via OkHttp to `getExternalFilesDir(null)`, then hands off to the system package installer via `FileProvider` (`ACTION_VIEW` + `application/vnd.android.package-archive`, since Android N+ blocks `file://` URIs across app boundaries). This is **not** a fully silent update — Android requires the user to approve both "install unknown apps" for this app (once, via `Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES`, handled by `UpdateDialog`'s `needsInstallPermission` state) and the actual install confirmation dialog each time (no way around this without being a system/device-owner app).

`AppUpdateManager.REPO_OWNER`/`REPO_NAME` point at `rpeters1430/Jellyfin-TV` — update these if the repo ever moves. The FileProvider authority (`${applicationId}.fileprovider`, declared in `AndroidManifest.xml` alongside `res/xml/file_paths.xml`) and `REQUEST_INSTALL_PACKAGES` permission exist solely for this feature.

### Target platform

TV-only: manifest requires `android.hardware.type.television`, declares leanback launcher intent, forces landscape orientation, and disables touchscreen requirement. Design and test interactions for D-pad/remote focus navigation, not touch.
